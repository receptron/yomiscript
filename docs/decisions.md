# Decisions (D1–D32)

D1–D13 decided on 2026-10-24. Those concerning syntax are drafts.

| ID | Date | Decision |
|---|---|---|
| D1 | 2026-10-24 | Reading priority has 3 tiers: inline specification {表記\|読み} > lexicon (in-document @lexicon and @import combined into one tier; within the tier @lexicon wins, and among @imports the later one wins; if the same orthography has several entries, an entry matching the context condition > [default], D13) > judgment from context (the model). Reflected in Section 1b |
| D2 | 2026-10-24 | Yomi-0 is a dense model and does not use MoE. MoE is considered only for future large LLMs |
| D3 | 2026-10-24 | Yomi-0 precision: train in BF16, distribute with 8-bit quantization. If accuracy drops, apply QAT (quantization-aware training). If there is almost no degradation, optionally also release a 4-bit version. Ternary training from scratch is kept only as a comparison experiment (hypothesis H9) |
| D4 | 2026-10-24 | Context-based disambiguation of readings is two-tiered: a small encoder (Yomi) handles most cases, and only low-confidence spots are delegated to a large LLM |
| D5 | 2026-10-24 | Yomi-0 training data: (1) auto-label a large corpus with pyopenjtalk + UniDic, (2) use human labels such as JSUT for evaluation and final-stage training, (3) for hard cases such as homographs, proper nouns and abbreviations, an LLM proposes candidates and a human checks them, (4) use ruby-annotated text and ASR transcripts as auxiliary data. Accent labels are the scarcest |
| D6 | 2026-10-24 | The acoustic back end's name is undecided. For now it is called the "KOE-IR back-end plugin" (Koe-S is one implementation of it) |
| D7 | 2026-10-24 | The lexicon (@lexicon, .koedict) can specify accent along with the reading. Notation: nucleus position with ', or [accent: N] (corresponding to UniDic's numeric notation). Syntax is a draft. Reflected in Section 1b |
| D8 | 2026-10-24 | Support dialects: @dialect (whole document), @lexicon(dialect: …), @import of dialect dictionaries, [dialect: …] (partial switch), and fall back to standard Japanese when no entry exists. v0.1 has only the dialect-tag framework; detailed notation, including Keihan-type accent registers (high-onset, low-onset), comes in a later version. Syntax is a draft |
| D9 | 2026-10-24 | Term definitions: Lexicon = the human-readable .koedict / @lexicon on the language side of KOE-IR (readings, accent, dialect). Memory = the key-value memory inside the neural network that is consulted during training and inference. Memory write = loading the lexicon's contents into Memory. Prose uses 「辞書」 and 「メモリ」, and the spec gives the English names alongside. 「記憶」 is not used. Device RAM is distinguished with qualifiers such as 「ユニファイドメモリ」 (unified memory) and 「RAM使用量」 (RAM usage) |
| D10 | 2026-10-24 | Design principle: language-independent shared weights + Memory modules swappable per language/dialect. At runtime only the shared weights and the one Memory currently in use are loaded, so RAM usage barely grows as more languages are supported (estimate). Which Memory to use is chosen explicitly via @dialect or a language specification (lang); the model does not route automatically. Differences from MoE are in the table below. To be tested by hypothesis H11 |
| D11 | 2026-10-24 | The swappable design of D10 is tentatively called MoLD (Mixture of Language-specific Dictionaries). MoLD is the name of the whole mechanism that connects the Lexicon and Memory via Memory write; its internal parts keep the D9 names. Name-collision check is in the note below |
| D12 | 2026-10-24 | MoLD inference has 2 modes: (1) fixed mode = explicitly select exactly one Memory via @dialect / language specification. Minimal RAM and predictable behavior. (2) auto mode = a lightweight classifier selects and switches Memory per sentence or span. For sentences mixing multiple languages, or texts where characters speak different dialects. Priority is explicit specification > automatic classification (same idea as D1). Caveats: a misclassification breaks reading and accent together. Switching incurs Memory loading latency, so frequently used Memories are kept resident in RAM, and classification is per sentence by default. Auto mode is evaluated in H11 |
| D13 | 2026-10-24 | Lexicon entries can have context conditions: register multiple readings for the same orthography with [context: …] (a domain name or nearby words), and specify the default reading with [default]. Selection order is entry matching the context > [default]. Incorporated into D1 as the ordering within the lexicon tier. Syntax is a draft. Reflected in Section 1b; compile-time handling and evaluation are in H12 |
| D14 | 2026-10-28 | Lexicons and inline reading hints are not part of YomiScript. YomiScript holds only resolved pronunciations (phonemes, prosody, language tags). `{表記\|読み}`, `@lexicon`, `@import`, `.koedict` and their conditions are inputs to the language-specific analysis step, specified in spec/lexicon/. The reading priority of D1 and D13 applies inside the analyzer. In YomiScript, braces mean only a language section |
| D15 | 2026-10-28 | Official names for the two modules around YomiScript: **Yomite** (読み手, "the reader") turns text into YomiScript; **Katarite** (語り手, "the narrator") turns YomiScript into sound. A Yomite can be a dedicated model (Yomi-0), a smart LLM, a rule-based analyzer or a person. Katarite plugins replace the provisional "backend plugins" name of D6. Lexicons (D14) are Yomite inputs |
| D16 | 2026-10-28 | We do not plan to build our own Katarite (acoustic) model. Koe-S (D6) is dropped from the plan. Katarite is provided by existing TTS engines through Katarite plugins, with Kokoro-82M as the reference |
| D17 | 2026-10-28 | YomiScript contains no language-specific scripts. Every language, Japanese included, is written in IPA with IPA-based prosody marks (Japanese accent: ꜛ ꜜ); the kana "display form" is removed. Kana labels (e.g. Yomi-0's JSUT-style output) are Yomite-internal and are converted with tools/yomiscript/kana2ipa.py. The web Katarite (demo/ys_web) accepts only IPA for Japanese. Chinese pinyin + tone digits is the same kind of exception and is to be replaced with IPA + tone letters |
| D18 | 2026-10-28 | YomiScript can carry both phonological prosody marks (ꜛ ꜜ, ˈ ˌ, tones) and phonetic pitch values `<f0:…>` (semitones relative to the speaker's register, per mora or syllable). Katarite uses only the values; turning marks into values is the Yomite's job (rules, a prosody predictor, or by hand). Kokoro's duration/F0 predictor is used as a separate component on the Yomite side. Pronunciation choices such as vowel devoicing and the t/d flap are written by the Yomite, not applied by the Katarite |
| D19 | 2026-10-28 | YomiScript uses IPA framing: an utterance is `<lang> /… ↘/` (or ↗), with ` \| ` for accent phrase and ` ‖ ` for breath group / pause; `^ $ ? # _` (JSUT style) are no longer YomiScript. The language tag is required (no implicit Japanese) and is BCP 47 language (+ region) only; sections are `{<lang> …}`. Dialect tags (`ja-x-osaka`) and the high-onset mark `=` are removed: a dialect is a Yomite setting, and its effect is already in the IPA and the pitch values |
| D20 | 2026-10-29 | The Yomite is not split into named stages (reading/accent vs. pitch values). An LLM can write complete YomiScript with pitch values directly (eval/llm_yomite: Claude Code and Codex, all outputs valid and usable). Rule-based prosody (demo/ys_web/web/yomite.js) and Kokoro's predictor (kokoro_prosody.js) are optional tools a Yomite may use to fill in values it did not write |
| D21 | 2026-10-29 | First target for the English Yomite + Katarite: behave exactly like the original Kokoro (eval/kokoro_parity). The Yomite runs Kokoro's own front end (KPipeline G2P and chunking) and rewrites its phoneme string as YomiScript losslessly; for that, YomiScript gains ` ↘ ` / ` ↗ ` inside an utterance and `<p:…>` for punctuation the engine uses as a prosodic cue. The Katarite uses the original's voice-pack index (len(ps)−1), returns single-language audio unprocessed, and its decoder export uses an STFT identical to torch's (demo/ys_web/exact_stft.py). No corrections to Kokoro's behaviour (e.g. question intonation) are made |
| D22 | 2026-10-29 | Japanese Yomite + Katarite, same target as D21 (yomite/ja_kokoro, eval/kokoro_parity). The Yomite runs Kokoro's Japanese front end (misaki Cutlet with UniDic, KPipeline chunking) and rewrites its phonemes as YomiScript IPA. The original drops 。 and 、 (and 「」『』・) and puts no '.' at the end; that is kept: the Yomite writes ↘ and ‖ where 。 and 、 stood (found by running the same G2P on the pieces of the text), and the Katarite renders Japanese ‖, inner ↘ and final ↘ as nothing but the word space, as the original's front end does (↗ stays '?'). Japanese words are separated by spaces, which the Katarite passes to Kokoro, as it does at ` \| `. Text the front end leaves as it is (Latin letters, a phoneme cut off at 510) goes into `<p:…>`. A final ↗ is '?' even after other punctuation (`<p:!> ↗` = '!?') |
| D23 | 2026-10-29 | YomiScript can carry the original text: `<t:…>` closes a span, and the units since the previous one are its reading (spec §2.7). Optional, never changes the pronunciation (the parser takes it out before reading the IPA, and Kokoro's input is identical with or without it). For showing the text being spoken (the chat plugin, subtitles) and for Katarites whose engine reads text (Supertonic 3, the Web Speech API), which choose for themselves how to use the text and the reading of each span. The Yomite's job stays writing YomiScript; there is no engine-specific notation |
| D24 | 2026-10-29 | Distribution: speech with few misreadings from the YomiScript the calling LLM writes (MCP server, CLI, gui-chat-protocol plugin). Everything shipped is TypeScript on npm, with no Python (Python stays in research and evaluation). Kokoro w16 in the browser, Kokoro fp32 (identical to the original) for the CLI and MCP; Supertonic 3 as a second Katarite. Plan and open items in docs/plan.md |
| D25 | 2026-10-30 | Japanese accent in the tools (CLI, MCP server, plugin): the calling LLM writes only the reading (the instructions still ask for no marks and no values), and `@yomiscript/ja-accent` adds the accent from a dictionary before Kokoro: OpenJTalk's front end (jpreprocess with NAIST-JDIC, as WebAssembly) analyses the original text (`<t:…>`), and each of its accent phrases that the YomiScript reads the same way, mora by mora, gets ꜛ / ꜜ and ` \| `; the rule Yomite renders only those phrases (`realize` `markedOnly`), at half strength (`jaScale` 0.5); every other phrase keeps Kokoro's own pitch, and the reading never changes. Why (eval/browser_tts/trials/accent_marks): Kokoro's own pitch follows about 60% of the dictionary's rises and falls; in blind listening tests it was heard as the worst accent in 9 of 10, 9 of 9 and 7 of 8 sentences where one was heard, and the halved rules never; letting the LLM write the marks changed readings (Claude: 市 いち -> し, 捕えて -> とらえて in 4 of 5 runs; Codex: broken phonemes), a dictionary cannot. A reading the dictionary disagrees with is left unmarked, which also keeps its own misreadings out. On by default (`--no-accent`, `YOMISCRIPT_ACCENT=0`, `accentBase: null` turn it off, which gives the original Kokoro, D21 / D22); the dictionary (28 MB) is downloaded from Hugging Face the first time Japanese is spoken. A YomiScript with its own marks or values is left as written |
| D26 | 2026-10-30 | The Kokoro reference moves past exact reproduction (D21, D22): it is improved where the original reads unnaturally, the original kept as the baseline. First change: the Katarite renders a Japanese ` ‖ ` as `, ` and an inner ` ↘ ` as `.`, as it does in English, instead of only the word space. The original's front end drops 。 and 、, so several Japanese sentences ran on without a break; the Japanese voices do pause at `.` and `,` (measured on 今日は晴れています。今日の日本経済を論じる。: 60 ms -> 470 ms at the sentence end; `。` is not in Kokoro's vocabulary). The final ↘ stays nothing. `plan(ys, { original: true })` gives D22's rendering for the parity checks |
| D27 | 2026-10-31 | Japanese accent in the tools, measured against commercial TTS (eval/prosody_ref): the same texts read by OpenAI (gpt-4o-mini-tts), Gemini (gemini-3.8-flash-tts) and ElevenLabs (eleven_multilingual_v2), each used only where Whisper with a kana prompt hears the right reading, are the reference; our pitch is compared mora by mora (DTW, sentence-centred RMS distance in semitones), a score that picked the variant heard as the worst in 17 of 22 sentences of the D25 listening tests. Three changes to `@yomiscript/ja-accent`: (1) the rules render the marks at 0.75 instead of 0.5 (`ACCENT_SCALE`; of 0.5 / 0.75 / 1 / 1.5 the closest); (2) the reading comparison accepts a consonant + j as the palatalized consonant (`kjoː` = `kʲoː`) and v as b; (3) a user dictionary (`src/userdict.ts`, built into the WebAssembly front end next to NAIST-JDIC): NAIST-JDIC's own rows at a lower cost where it prefers a reading LLMs do not write, so the phrase gets its accent; the first two are 日本 and 日本人 read ニホン. The reading spoken never changes. On Claude's 460 YomiScripts: Kokoro's own pitch 3.14, D25 2.92, D27 2.87 (closer than D25 on 191 items, farther on 132). Not kept: joining a verb after て (いる, います) to the phrase before, or leaving it unmarked; both were farther from the references than D25. By ear (JSUT BASIC5000_0201-0300, rendered from the hand-labelled marks at 0.75 / 1 / 1.5 / 2): 0.75 to 1 sounds right, 1.5 and 2 too strong |
| D28 | 2026-10-31 | Japanese pitch values from the whole sentence, rendered as a line. (1) The Tokyo rule Yomite writes three values per mora (the start, middle and end of its voiced part) from a linear model over the marks of the whole sentence (`packages/core/src/ja_contour.ts`): H / L and the nucleus, downstep after accented phrases, the place in the breath group and in the sentence, a pause or a question after the mora. Osaka keeps the phrase rule. (2) The Kokoro Katarite renders a Japanese section's values as points over each mora's voiced frames, joined by straight lines and smoothed over 7 frames (about 90 ms), and moves the whole section to the level of the engine's own F0 (`packages/kokoro/src/render_ja.ts`). Before, each mora's value was held flat over all its frames, and each accent phrase was moved to the engine's level, which undid every difference between phrases (the 0.6 semitone declination step included); a final mora's duration also covers the silence after it, which hid a final rise. Non-Japanese sections render as before. (3) The accent step renders at full strength (`ACCENT_SCALE` 1). Checked by ear on JSUT BASIC5000_0201-0300: better step by step than the hand-labelled marks with the earlier rule; a question rise added by rule on top was too strong and is not kept. The Tokyo outputs in `test/fixtures/presets_realized.json` are regenerated (Osaka unchanged) |
| D29 | 2026-10-31 | The Japanese pitch model of D28, refitted with more of what the marks say. (1) Each mora's three values now also depend on the two morae before and the two after it (their features, weighted by distance), and on what the mora is: its vowel, ɴ, the geminate, a long vowel, a voiceless onset; on how far it is from the end of its breath group, its accent phrase's place in the breath group, and a few products of the D28 features (`packages/core/src/ja_contour.ts`, 45 features, 675 coefficients). (2) The model was fitted to the pitch at the points where the Katarite puts the values (the start, middle and end of each mora's voiced part, a final mora's included up to 0.3 s past its end), not at 20 / 50 / 80% of the mora as in D28, which had hidden most final rises, and to sentences read as questions where the text is one. Checked by ear on JSUT BASIC5000_0201-0300: heard as far better than D28 and nearly right throughout, the questions included; one sentence (0228, 五千円あれば) runs 円 and あれば together. The Tokyo outputs in `test/fixtures/presets_realized.json` are regenerated (Osaka unchanged) |
| D30 | 2026-10-31 | The Kokoro Katarite lengthens a Japanese moraic ɴ directly followed by a mora without an onset (千円あれば, 原因, 恋愛) to 1.5 times Kokoro's predicted duration, and that vowel to 1.25 times (`lengthen` in `packages/kokoro/src/plan.ts`, applied to the predicted durations in `engine.ts`). Kokoro runs the two together: on JSUT BASIC5000_0201-0300 such an ɴ was 0.66 of the human reader's length and the vowel 0.85, against 0.94-1.00 for every other kind of mora (relative to each sentence's rate); 0228's んえんあ took 275 ms, against 362 ms for the human reader. Kept as a Katarite rule, not as a duration notation in YomiScript: the ɴ is a full mora in any reading, and Kokoro's short one is the engine's fault, which other Katarites need not share; a notation for chosen lengths (emphasis, slow reading) is left until such a use is defined, and would override this default. Durations are as predicted with `plan(ys, { original: true })` and outside Japanese. Checked by ear on 0228, 0208, 0214, 0240 and 0267: good enough (2 and 1.4 were also tried) |
| D31 | 2026-11-01 | The Japanese dictionary accent looks the YomiScript's own words and readings up instead of letting OpenJTalk analyse the text again (`packages/ja-accent/src/lookup.ts`; the WebAssembly's `candidates`, `conn`, `label`). The LLM has already split the text into words (`<t:…>`) and read each one from the context; D25 threw both away, let OpenJTalk choose words and readings again, and left every accent phrase it read another way unmarked, so the words the LLM reads from the context (市 いち, 今日 こんにち, 上手 かみて, 角 かど) lost their accent. Now every NAIST-JDIC and user-dictionary entry of the sentence is listed, and the cheapest path (OpenJTalk's word and connection costs) is taken whose morae read as the YomiScript does (`sameMorae`, the comparison of D25 and D27), with the same number of morae at every word boundary; an entry may cross a boundary (の|で read as one ので); a word with no Japanese morae takes any entries; a word no entry reads that way is taken as OpenJTalk's analysis reads it, at a large cost (that phrase stays unmarked); an entry starting inside a word joins the accent phrase before, so a word is never split between two phrases. OpenJTalk's rules (NJD: accent phrases, accent combination, digits) then run on the path. The reading spoken never changes. Why (eval/accent_lookup): on Claude's 465 YomiScripts of eval/prosody_ref/mismatch.mjs the marked accent phrases go from 92.2% to 97.2% (read another way: 5.3% to 1.1%; not on word boundaries: 2.4% to 1.7%); by word, 245 newly marked, 5 no longer marked, 17 marked differently; in a blind listening test of the 22 texts whose marks change (one listener), the new marks were more natural in 7, the old in none, the same in 12, both unnatural in 3. `analyze` is rebuilt on the same tokenizer and gives the same NJD and labels as before on 3,120 texts; `{ analysis: true }` keeps the D25 / D27 marking as the baseline. Not yet: numbers with a counter (9時, 20日), whose readings OpenJTalk's digit rules make after the dictionary, are still taken as the analysis reads them |
| D32 | 2026-11-02 | The Japanese dictionary accent keeps the accent phrases a YomiScript writes itself (`packages/ja-accent/src/lookup.ts`, `ownPhrases`): when a Japanese section has a ` \| `, each word after a ` \| ` or ` ‖ ` starts an accent phrase and every other word joins the one before (the `chain` of OpenJTalk's rules on the D31 path), so the dictionary's accent and OpenJTalk's accent combination go into those phrases; an entry starting inside a word, a word with no Japanese morae and the word after it are left to OpenJTalk; a YomiScript with no ` \| ` is marked as before. Why (eval/llm_phrasing): the accent phrases are D31's largest error against JSUT's hand annotation, and an LLM asked for them (one more line of instructions) writes them closer to it (boundary F1 92.5, against 87.7 for OpenJTalk's rules and 91.3 for 17 rules learned from JSUT; Claude, 414 sentences of the test half) without reading worse (428 of 500 sentences read as the gold, against 426 and 428 in two runs without the line); with them the accent is as close to the gold as with the learned rules (gold phrases right 63.3%, D31 60.7%). The instructions the tools give (`YOMISCRIPT_INSTRUCTIONS`) do not ask for ` \| ` yet: that waits for a listening test |
| D33 | 2026-11-03 | Japanese pitch values can be predicted from the text by a small model (`packages/ja-accent/src/pitch.ts`, `pitchYomite`). A two-layer bidirectional LSTM (1.78 million parameters, 6.7 MB, downloaded from Hugging Face, CC BY-SA 4.0 from its training texts) reads the morae with the dictionary's nuclei and adds to each mora's three values (D29's features refitted to Qwen3-TTS); it is written in plain TypeScript, so `@yomiscript/ja-accent` gains no dependency and no Python. No notation changes (D18: the Yomite turns marks into values; the marks stay in the YomiScript, the Katarite speaks the values). Why (eval/qwen_prosody): choosing the nucleus from the text closes 7% of the distance from the dictionary's nuclei to the nuclei read from Qwen's pitch of the same sentence (1.871 to 1.494 semitones on 1,214 unseen sentences); predicting the values and training on the distance itself closes 74% (1.592), with no flattening. Blind, 12 sentences, one listener: unnatural the dictionary's nuclei 6, the nuclei read from Qwen 3, the predicted values 3, Qwen 2. A second hearing through the TypeScript path: 5, 3, 2, 2. The default in the CLI, the MCP server and the plugin (off with `--no-pitch`, `YOMISCRIPT_PITCH=0`, `pitchBase: null`), falling back to the dictionary accent if the model cannot be loaded; the demo's accent editor keeps the dictionary and has a button for it. Made the default by the listener's decision on the single-sentence results: it was trained on single sentences only and several sentences as one utterance (`eval/qwen_prosody/pitch_listen_long.mjs`) have not been listened to |
